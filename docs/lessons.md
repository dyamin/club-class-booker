# Lessons: problems we hit, and the rule that stops them from coming back

Each row is a real problem from building and testing this program. The rule is already in the code or in the way we work. When you meet a new problem, add a row, and add a fake mode and a test that reproduces it.

## On the real app

| # | Problem | Cause | Rule now |
|---|---|---|---|
| 1 | The first dry run could not switch to Alex | The screen tool returns **native pixels** (2048 x 1600 on Retina); the program reads positions in **points** (1024 x 800) | One place scales every screenshot to window points (`MirroirScreen.screenshot`, `region_png`). The fake tool can return Retina pictures (`--retina`) |
| 2 | A tap on the Favorites tab did nothing | The first click on a window that is not in front only activates it | Activate the app first; **verify every navigation step** by what the screen shows, not by "the tap was sent"; tap again. The fake app can lose taps (`favorites_tab_lost`) |
| 3 | The scan stopped: "two screens have no class in common" | A swipe **flings** the list by many cards | Keep the overlap check (it was right). Scroll by accessibility page, which overlaps. Never assume a swipe moves a fixed distance |
| 4 | A swipe opened a class page | The drag started on a card | Do not start a drag on a card; close any page you opened by mistake |
| 5 | The app showed the selector with a spinner for ever | No session (it was logged out) | Look once at the screen; on the login screen stop and tell the phone. Restart a stuck app once, never in a loop |
| 6 | The app logged out by itself | A forced update (new version) | The update popup is its own state: report "update the app" and stop |
| 7 | **The login was locked for 10 minutes** | Three code requests in a row. My script called the "send code" press **twice inside one `print()` line** | An action with a side effect runs **once**; keep its result in a variable. A login has a limit of 3 requests per 10 minutes: count them. Never repeat a login step "to be sure" |
| 8 | Typing did nothing, or could go to the wrong app | Typing goes to the **front app**; IntelliJ, Chrome and Terminal kept taking the front. The text field was not focused | Press the field by accessibility, check the front app right before typing, and type at once. If the check fails, do not type |
| 8b | The phone field held "05000an050000000005000000000" and the app answered "יש להזין מספר טלפון נייד תקין" | The field **keeps text** from earlier tries (also when the first typing failed), and a new number is appended to it. Accessibility does not show the typed text | Clear the field first (select all, delete), type, then **read the field from the screen with OCR** and send only when it is exactly the number. The helper does this; the check was tested live on the real screen |
| 8c | After "send me a code" the program waited a fixed 6 seconds and reported "unknown", but the code screen came later | The app answers in a few seconds or in more than 20: the time is not fixed | Wait by **looking** (a screen read every second, at most 25 seconds) until the screen is the code screen, the lock popup or the update popup. The wait only looks: it never presses again. The same wait is used after the code is typed |
| 9 | One run raised `IndexError` and the cause was not found | A pixel read outside a small picture | A reader of pixels must return "not sure" for a position outside the picture, never raise |
| 10 | The reader said "other" on a screen we thought was fine | The reader prompt had guessed wording | Use the real Hebrew words from the app (see `club-app-field-notes.md`). Prefer accessibility text: exact, free, no guessing |
| 10b | The calendar check after a booking would have timed out, although the event was saved | On this Mac a filter over one calendar (`every event whose start date ...`, 1100+ events) takes **20-30 seconds**, whatever the range. Written as `repeat with e in (every event ... whose ...)`, the filter ran **again at every property read**: one event took **181 seconds** (limit 90). Measured live on 2026-10-13 | Run the filter **once** into a variable (`set evs to (every event ... whose ...)`), then loop over `evs`: the same window took 22 seconds. Count the number of Calendar passes in every new feature (one per calendar, not one per class), and read results back **inside** the script that made them. A text test guards the pattern. A faster way (EventKit helper) is a later improvement |
| 10c | The first unattended opening (16:30) did nothing: the Mac was asleep, then locked | **launchd does not wake a sleeping Mac, and nothing can click on a locked screen.** The tick agent ran at 16:00, and the next job came at 16:30 (a calendar-time job that fired in a short wake-up): the screen was locked. The program said so: one reminder "the Mac is locked" at 16:30:07, naming the class | The designed path is right, and it was proven by accident. The reminder now names the person, the class and the time, so the user can register by hand from the phone (the program then skips that class). A real fix needs the Mac awake and unlocked at the openings (an optional scheduled wake with `pmset` needs an administrator) |
| 10d | The app was logged out hours after the login | A session lasts between 3.5 and 7 hours (login 12:00, still valid 15:33, gone by 19:05) | The 5-minute tick looks at the app once in the hour before an opening and tells the phone when it is logged out or needs an update, while there is time to log in. The login itself stays guarded and supervised (`login request`, `login code`) |
| 10e | A booking waited for the calendar editor of the booking before it | The editor path costs about a minute per class (two 20-30 s Calendar passes, the editor clicks, a rename pass). With three people opening at the same minute the third tap came 3-4 minutes late | **Counted, time-critical actions first; slow, safe-to-repeat steps after.** With `calendar_audit = write` a booking only taps and closes the dialog; the audit adds the events afterwards (3 s each, one pass per calendar) |
| 10f | A "first look" that is not first: taps on a screen nobody looked at | The Classes tab (640, 775) lies inside "send me a code" on the login screen. A session can end between the check of the selector and the first tap | One screen look before each pass of blind taps; raise "logged out" for the login, code, lock and update screens (`Runner._stop_if_blocked`) |
| 10g | Runs failed with "Failed to capture screenshot" at 18:58 and used up two of the three failures of the day | The **display was asleep** (the Mac was awake and the session not locked): the screenshot is black and the app window has no size | A sleeping display counts as unavailable, like a locked Mac (`system.screen_unavailable`, read through CoreGraphics). It is woken **once, and only when a class is due** (`wake_if_only_asleep`), never at every tick, so the display can sleep |
| 10h | The program could not tell what a class page shows, or which classes a person holds | The spec called both "not verified" | Looked at the real app (read-only): the booked tab lists every booked class with a "ביטול" button; a class page lists the attendees. They are fixtures now (`ax_booked.json`, `ax_details.json`, names replaced) |
| 10i | A cancel is irreversible, and a wrong press could cancel the user's own class | The user also registers by hand, and the cards of a list each have a "ביטול" button | **One guard** (`Runner.cancel`): only the program's own standing bookings of that person; the press is bound to **the card of the same reading** (`ax press-in-card`: the card must be on the screen exactly once); the message after the press is read, and only a success message is closed; write before the press; never repeat; the class the user kept must still stand; verify afterwards; mutation-tested. A class registered by hand has no booking record. A booking the list shows open again loses its record |
| 10k | The independent review of the questions code found 5 critical and 8 important problems that 445 green tests did not | The tests play what we think the app does; they cannot show a press landing on the wrong card, a stale answer, or a restart that logs the app out | Fresh reviewer on the irreversible code **before** it is switched on; mutation-test every safety rule; a failure of a new step never stops a booking; an answer that cannot be applied is kept and retried, never lost silently |
| 10j | The answers script compiled and passed its tests, but failed on the real Reminders (error -1700) | `paragraph 1 of (body of r)` needs text, and `body of r` through a list reference is not text. A **compile check proves the syntax, not the meaning**, and the fake plays what we think the app does | Every AppleScript template gets **one real run** (create, read, delete a labeled test item) before it is trusted. `(body of r) as text` first. A text test keeps the pattern out |
| 10m | Even with no timer, a refresh of the plan or an answer could start while the user was working, and its clicks went into the user's work | The only check was "idle for 10 minutes" **before** the run. The user can come back one second later, and a run takes minutes | **An attention guard before every click** (`attention.py`): the program knows the time of its own last click (its clicks reset the Mac's idle time too, measured: 0.1 s after a click), so an input that is newer than that is the user. A non-urgent run stands back at once, with no failure, no message and no used-up refresh; a class that is opening waits once for a pause in the typing and then books. The stop is a `BaseException` so no "this step failed, go on" handler swallows it. A booking that was begun is finished; a booking is never written ahead of a tap that the guard stopped (mutation-tested) |
| 10l | The program took the mouse and opened the app every few minutes, and the user could not work | A polling tick (5, then 15 minutes) started runs: retries of a failing opening, the daily re-plan, a look before openings. A timer wakes the program when nothing is due | **Wake only at the time a class opens, and never before.** One persistent launchd agent per planned opening, installed in advance; no timer. A locked Mac or a logged-out app is waited out by the opening agent itself (20 minutes, a look every 15 seconds); a retry is an agent armed 5 minutes later, 6 times at most. Non-urgent work (the plan refresh, applying an answer) waits until the user has been away 10 minutes |
| 10o | Five reminders stood on the phone at 17:18 and the user asked why there were so many: a "Mac is locked" message (16:45) and a "Problem (Alex)" report (12:08) were still there, long after the class was booked | The program sent a message when a problem started and never took it back; only the two-day prune removed it | **A message about a problem is tagged and remembered, and deleted when its problem is gone** (the person's next good run; a login message when any person can run; a message about two people waits for both). The "told today" counter is cleared with it, so a problem that comes back is told again. Stood-back and dry runs prove nothing. A failing phone keeps the message for the next run (14 mutations of these rules are caught). Booking reports and questions are left alone |

The phone had 5 "the Mac is locked" reminders, a "logged out" one and "to check" ones; the runs said "Failed to capture screenshot" and "window not visible"; the first automatic login failed (`login_error`, no reason in the log) | The user was away (Sabbath): the Mac turns the display off and locks at once (`sysadminctl -screenLock` says "immediate"). ## In the way we work

| # | Problem | Rule now |
|---|---|---|
| 11 | A multi-file edit script failed halfway and left the tests broken | Edit scripts are **all or nothing**: check every anchor first, write nothing if one is missing or not unique |
| 12 | The fake app was too kind: it never lost a tap, never got stuck, never changed size | A real defect gets a **fake mode** in `tests/fake_app.py` / `tests/fake_mirroir.py` and a test that fails first |
| 13 | A guess about coordinates ("1:1 with the screenshot") was true only on one display | Write down which coordinate space a number is in. Test with the other space too |
| 14 | A tool I was allowed to use could not do the job (typing) | Look for another channel that is already allowed (accessibility), or ask. Do not widen a safety setting without asking |
| 15 | Several things at once (the user moving windows, focus changes) hid the real cause | Do one action, look at the screen, then decide. Do not stack blind actions |
| 16 | Personal data in test files | Fixtures keep the structure, not the people: trainer names and phone numbers are replaced |

## Checks before you touch the real app

1. Is the Mac unlocked and the app in front? (`ax dump` or a screenshot)
2. Does the screen show what you think it shows? (one look, one decision)
3. Is the action **counted** (a login code, a booking)? Then run it once and keep the result.
4. Can the action be undone? If not, ask first.
